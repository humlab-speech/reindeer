# reindeer amendment plan (from 2.2.0)

Companion to `dev/REINDEER_ASSESSMENT_2.2.0.md` (the assessment). That file says
what is wrong; this one says what to change, in what order, and what proves it.
Item IDs (A1, P3, §3.4, …) refer to the assessment. Supersedes
`dev/REINDEER_REMEDIATION_PLAN.md`.

Date: 2026-10-11. Base: `main` @ `b15b50a`.

## 0. Rules for every work package (WP)

- **Test first.** Each WP starts by adding the regression test that reproduces
  the assessment finding and fails on `main`. A WP is done when that test is
  green and nothing else turned red.
- **One WP, one commit** (`fix:`/`refactor:`/`perf:`/`feat:`), NEWS entry in
  the same commit when behaviour visible to users changes.
- **Gates between phases.** Do not start a phase with a red gate.
- **No fix twice.** If a later phase rewrites a code path, the earlier phase
  does only the minimal fix + test; the test then guards the rewrite.
  (Example: A4 is a one-line fix in an executor that P2 deletes. The test
  survives, the fix does not need to.)
- Effort: S ≤ ½ day, M 1–3 days, L > 3 days.

## 1. Releases

| Release | Phases | Character |
|---|---|---|
| 2.3.0 | 0, 1, 2 | Deletions + every silent-wrong result fixed. No new API. |
| 2.4.0 | 3 | EQL/navigation parity with emuR. Times shift by ½ sample (documented). |

Rationale for the order (assessment §9, adjusted): correctness before power,
because per-bundle DSP and default-on caching would otherwise reproduce wrong
results faster and persist them. Two power items move forward because they are
deletions that also remove bugs and speed up the dev loop: P1 (worker pools;
also kills the A9 `bad_weak_ptr` crash) and P12 (test cost).
